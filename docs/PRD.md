# GeoCompare 产品需求文档

**版本**：0.2.0（MVP 规划）  
**状态**：待技术验证  
**更新时间**：2026-10-09  
**产品形态**：开源 npm React 组件库  
**目标发布**：`0.1.0`

## 1. 产品概述

GeoCompare 是一个面向遥感与地理空间栅格数据的 Web 对比组件。它建立在 MapLibre GL JS 之上，负责将两份具有地理参考的数据组织成可嵌入、可复用的对比界面。

GeoCompare 不重新实现地图渲染、栅格解码或遥感分析算法。它的价值在于把地图同步、对比交互、数据元信息、图例和错误状态组合成一个一致的 React API，降低开发者搭建影像对比页面的成本。

### 1.1 一句话价值主张

让开发者在 5 分钟内把两份遥感影像或栅格图层接入一个可解释、可交互的对比界面。

### 1.2 产品边界

| 属于 GeoCompare | 不属于 GeoCompare |
| --- | --- |
| 对比视图与交互 | 地图引擎 |
| 双地图视图同步 | GeoTIFF/COG 解码 |
| Swipe、并排对比 | 影像托管与下载 |
| 日期、来源、波段等元数据展示 | 服务端影像处理 |
| 图例与色阶说明 | 自动变化检测与 AI 推理 |
| 配置导入导出 | STAC 搜索服务与账号系统 |

## 2. 背景与问题

目前开发者通常需要自行组合 MapLibre、地图对比插件、图例、元数据面板和响应式布局。常见问题包括：

1. 两个地图实例的平移、缩放和销毁逻辑容易出现不同步或资源泄漏。
2. Swipe 交互容易完成，但日期、来源、波段和色阶说明经常缺失，用户难以判断差异是否真实。
3. 不同数据的色阶和单位可能不一致，直接并排展示会造成误读。
4. 每个项目都要重复实现加载失败、容器尺寸变化、移动端布局和 React Strict Mode 兼容。
5. 现有方案多聚焦地图能力或栅格能力，缺少一个面向“遥感对比工作流”的轻量 UI 层。

## 3. 目标与成功标准

### 3.1 MVP 目标

在 1–2 周内发布一个可安装、可演示、可集成的 `0.1.0`：

- 支持两份 MapLibre style 或已注册图层的对比。
- 支持 Swipe 与 Side-by-side 两种模式。
- 支持地图视图同步、影像元数据和图例。
- 支持清晰的加载、空状态和错误状态。
- 提供完整 TypeScript 类型、README 和在线 Demo。

### 3.2 成功标准

工程验收：

- 在一个全新的 React + Vite 项目中完成安装并运行示例。
- `lint`、`typecheck`、`test`、`build` 全部通过。
- 组件卸载后无重复地图实例、事件监听或未处理异常。
- 关键交互具备自动化测试。

用户验收：

- 新用户从 README 到第一个可运行对比页面不超过 5 分钟。
- 至少 5 位目标用户试用或评审。
- 至少收集 3 条可复现的有效反馈。
- 发布后 30 天内获得至少 2 个外部项目集成（实验目标，不是市场承诺）。

## 4. 目标用户与使用场景

### 4.1 目标用户

**遥感/GeoAI 开发者**：展示不同时相影像、模型输入与输出或分类结果。  
**GIS Web 开发者**：在已有地图应用中增加影像对比能力。  
**科研与数据平台开发者**：构建城市变化、灾害影响、植被变化等可解释的展示页面。

### 4.2 典型场景

1. 对比同一区域两个日期的卫星影像。
2. 对比原始影像与土地覆盖分类结果。
3. 对比两个处理版本或两个模型输出。
4. 对比两份指数栅格，并分别展示数值范围和单位。

### 4.3 非目标用户

- 需要在线地图编辑、空间分析或数据管理平台的用户。
- 需要直接上传任意 GeoTIFF 并自动完成投影、重采样和渲染的用户。
- 需要在组件内运行变化检测、NDVI 或 AI 推理的用户。

## 5. 产品原则

1. **先做对比工作流，不做通用 GIS 平台。**
2. **底层能力复用成熟项目，产品价值集中在组合体验。**
3. **差异必须可解释。** 不把视觉差异自动描述为真实地理变化。
4. **色阶显式声明。** 未声明时不假设两份数据可使用同一图例。
5. **默认安全。** 配置导出不得包含 token、密钥或完整请求头。
6. **失败可理解。** 网络、样式和容器问题应提供可定位的错误信息。

## 6. MVP 功能范围

优先级定义：P0 为发布阻塞项，P1 为首版后优先项，P2 为长期探索项。

### 6.1 P0 功能需求

#### F-01 双数据源配置

开发者可以分别传入 `before` 和 `after` 配置，包括：

- `id`、`label`；
- `acquiredAt`、`source`、`bands` 等可选元数据；
- MapLibre style URL 或 style specification；
- 可选图例配置。

验收标准：配置缺少必填字段时，在开发环境给出明确错误；合法配置可创建两侧地图。

#### F-02 Swipe 对比

- 提供可拖动的垂直分割线。
- 支持鼠标、触摸和键盘操作。
- 支持初始位置配置，范围为 `0–1`。
- 显示 Before/After 标签。
- 滑块移动不会改变地图中心、缩放、旋转或俯仰。

#### F-03 Side-by-side 对比

- 左右显示两份数据。
- 两侧共享初始视图并保持同步。
- 支持从 Swipe 切换到 Side-by-side，且保留当前视图。
- 窄屏下采用上下布局或明确的降级布局。

#### F-04 视图同步

至少同步：中心点、缩放级别、bearing、pitch。

验收标准：任一侧操作后，另一侧在一个渲染周期内到达相同视图；不会因双向监听产生循环更新。

#### F-05 元数据面板

显示每份数据的名称、日期、来源和波段信息。字段均可选；未提供时不展示空标签。

验收标准：元数据内容与输入配置一致，不自动推断或修改用户提供的日期、单位和来源。

#### F-06 图例与色阶

- 支持独立图例和共享图例。
- 支持标题、单位、最小值、最大值、颜色 stops 和标签。
- 共享图例必须由调用者显式选择。
- 非法色阶（重复值、空 stops、范围反转）应在配置校验阶段报错。

#### F-07 生命周期与状态

覆盖初始化、加载中、加载成功、空配置、样式加载失败和运行时错误。

验收标准：React Strict Mode 下不会产生重复实例；卸载时地图、插件、事件和临时 DOM 均被清理。

#### F-08 配置导入导出

- 提供可序列化的配置对象或导出函数。
- 导出内容不包含访问令牌、密钥、请求头和运行时地图实例。
- 导入后可以恢复对比模式、初始视图、元数据和图例。

### 6.2 P1 功能需求

- Opacity 叠加模式，但必须支持图层级别 opacity，而不是简单降低整张地图透明度。
- 时间轴与多时相数据切换。
- COG、STAC Item 的独立适配器。
- URL 状态同步与可分享链接。
- 多波段选择和 RGB 组合。
- 基础键盘无障碍增强与完整 screen reader 文案。

### 6.3 P2 功能需求

- 变化检测或差异计算展示。
- Leaflet、OpenLayers、Cesium 等其他地图适配器。
- 统计面板、直方图和科研报告导出。
- 面向团队的云端配置与协作能力。

## 7. 用户流程

### 7.1 开发者集成流程

1. 安装 `@morainet/geocompare`、React 和 MapLibre peer dependencies。
2. 引入 MapLibre 与 GeoCompare 样式。
3. 传入 `before`、`after` 和 `initialView`。
4. 选择 `swipe` 或 `side-by-side` 模式。
5. 根据数据实际含义配置独立或共享图例。
6. 在真实项目中替换 style URL 和元数据。

### 7.2 终端用户流程

1. 页面显示两份数据的名称、日期和来源。
2. 用户拖动 Swipe 滑块或查看并排视图。
3. 用户平移、缩放地图，两侧保持地理位置一致。
4. 用户查看图例和单位，理解颜色含义。
5. 数据加载失败时，看到明确的错误提示，而不是空白地图。

## 8. API 方向（初稿）

```ts
export interface CompareImage {
  id: string;
  label: string;
  acquiredAt?: string;
  source?: string;
  bands?: string[];
  style: string | maplibregl.StyleSpecification;
  legend?: LegendConfig;
}

export interface GeoCompareProps {
  before: CompareImage;
  after: CompareImage;
  mode?: "swipe" | "side-by-side";
  initialPosition?: number;
  initialView?: {
    center: [number, number];
    zoom: number;
    bearing?: number;
    pitch?: number;
  };
  legendMode?: "independent" | "shared";
  className?: string;
  style?: React.CSSProperties;
  onModeChange?: (mode: "swipe" | "side-by-side") => void;
  onError?: (error: GeoCompareError) => void;
}
```

API 在技术验证后冻结。首版不承诺兼容任意栅格格式；数据如何作为 MapLibre 图层呈现，应由调用方或独立适配器负责。

## 9. 非功能需求

### 性能

- 首版只维护两个地图实例，不承诺大规模多视图性能。
- 不重复处理栅格数据，不在组件内做像素级计算。
- 视图同步不得造成明显卡顿或事件风暴。
- 组件应能在常见桌面浏览器中流畅拖动 Swipe。

### 可访问性

- Swipe 控件提供可聚焦元素、键盘方向键操作和当前值语义。
- 模式切换控件具备可读名称和选中状态。
- 错误和加载状态可被辅助技术感知。

### 兼容性

- 支持现代 Chromium、Firefox、Safari。
- 支持 React 18+，具体版本在 `package.json` 中声明。
- 以 ESM 和 TypeScript declaration 为首要发布格式。

### 安全与隐私

- 不上传影像、配置或用户数据到 GeoCompare 服务端；首版无服务端。
- Demo 不在前端代码中暴露私有 token。
- 导出配置默认过滤凭据和请求头。

## 10. 测试与验收

### 自动化测试

- 配置校验：必填字段、初始位置、图例范围和非法配置。
- 核心状态：模式切换、滑块位置、视图同步防循环。
- React 组件：元数据、图例、加载、错误和卸载。
- 浏览器集成：双地图创建、Swipe 拖动、视图同步、响应式布局。

### 发布前手工检查

- 地图样式 URL 无效。
- 影像服务 CORS 或 HTTP Range 不可用。
- 慢网络与中途失败。
- React Strict Mode 重复挂载。
- 容器从隐藏变为可见、窗口尺寸变化。
- 移动端触摸和键盘操作。
- 共享图例与独立图例的视觉含义。

### 发布阻塞条件

- 任一核心模式无法稳定创建或销毁地图。
- 两侧视图不同步或存在明显循环抖动。
- README 示例无法在新项目中运行。
- 构建产物错误地打包 MapLibre 或缺少类型声明。
- Demo 使用未获授权或无法稳定访问的公开数据。

## 11. 数据与 Demo 需求

首版至少提供一个“城市变化” Demo：同一区域两期公开影像，包含采集日期、来源、许可说明和图例。

Demo 数据必须满足：

- 允许公开展示或明确属于可公开使用的数据。
- 不依赖个人 token，或使用安全的环境变量配置。
- 在页面中标明来源、日期、坐标系和限制。
- 能在服务不可用时展示可理解的错误状态。

后续可增加植被指数和原始影像/模型结果两个 Demo，但不以它们阻塞 `0.1.0`。

## 13. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| MapLibre 对比插件版本不兼容 | 高 | 第 1–2 天完成最小 PoC，并锁定版本 |
| 双地图资源消耗较高 | 中 | 首版限制两个实例，不承诺大规模并行 |
| COG、CORS、Range 或投影限制 | 高 | 首版不承诺任意 COG，适配器独立演进 |
| Swipe 功能本身缺乏差异化 | 中 | 强调遥感元数据、图例和可复现配置 |
| 共享色阶造成误导 | 高 | 共享图例显式配置，默认独立图例 |
| 公共 Demo 数据不稳定 | 中 | 使用可替换数据源并准备静态降级示例 |
| API 过早冻结导致返工 | 中 | 先完成技术验证，再发布 0.1.0 并标注实验性 |

## 14. 发布后验证计划

发布后 30 天只关注以下信号：

- 是否有真实项目成功安装并集成。
- 用户是否能区分并正确使用独立/共享图例。
- 哪些数据接入方式最常见，是否需要独立适配器。
- 模式切换和视图同步是否在真实项目中稳定。
- 用户反馈的问题是“缺少功能”还是“当前集成仍然太复杂”。

暂不以 Star、npm 下载量单独判断产品成功；将下载量与外部集成、Issue 质量和用户反馈结合分析。

## 15. 待验证问题

在进入完整实现前必须回答：

1. MapLibre 当前版本与目标对比插件是否能稳定支持两个 style 的同步。
2. 调用方更希望传入完整 style，还是传入可挂载的 raster/vector source 和 layer。
3. 遥感开发者是否愿意使用组件提供的元数据/图例模型，而不是自行渲染。
4. Swipe + 元数据 + 图例是否比现有插件组合明显减少集成代码。
5. 目标用户最需要的是 Swipe、时间轴、COG 接入还是变化检测展示。

这些问题在用户访谈和最小原型验证前保持开放，不应通过继续增加 P0 功能来掩盖。
